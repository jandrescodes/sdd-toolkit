# Technical plan — Spec 002

Everything lives under `plugins/sdd/` (constitution principle 1). The only
code is bash in `tests/validate.sh`; the rest is prompts and Markdown
templates, so "implementation" means writing instructions an agent follows.
The new skill is the single place where document logic lives; commands only
call into it.

## Module structure

- `plugins/sdd/skills/sdd-documents/SKILL.md` → all document logic: profile
  resolution, closed-feature detection, per-document derivation, review list,
  diff/approval, `.gitignore` handling, schema refresh procedure, and the
  "hand-written documents" notice. Natural-language triggers in its
  `description` (FR-1–3, 14–34, 40–50).
- `plugins/sdd/skills/sdd-documents/templates/` → seven original MIT
  templates, authored from scratch: `schema.md`, `app-flow.md`, `ux-brief.md`,
  `prd.md`, `trd.md`, `acceptance.md`, `changes.md` (FR-33, 36).
- `plugins/sdd/commands/docs.md` → thin wrapper: passes `$ARGUMENTS`
  (`<name> [feature]`) to the skill and carries no rules of its own (FR-16).
- `plugins/sdd/commands/validate.md` → new steps after the verdict: roadmap
  update, schema refresh through the skill's procedure, validation date,
  "updated files" list; `Edit` added to `allowed-tools` (FR-4–10, 40, 47, 49).
- `plugins/sdd/commands/change.md` → after the diff is approved, append the
  `## Changes` entry; defines the entry format (FR-11–13).
- `plugins/sdd/skills/sdd-flow/templates/AGENTS-sdd-section.md` → `Docs
profile` line, `deliverables/` in the deploy exclusion, `/sdd:docs` as a
  cross-cutting command (FR-1, 32).
- `plugins/sdd/skills/sdd-flow/templates/validation.md` → `**Date:**` line and
  an "Updated files" block. `templates/tasks.md` → closeout line says
  `/sdd:validate` also moves the feature to Done (FR-7, 40).
- `plugins/sdd/skills/sdd-flow/templates/roadmap.md`, `sdd-flow/SKILL.md`,
  `docs/constitution.md`, `docs/roadmap.md`, `README.md` → drop "by hand"
  wording for the roadmap (FR-51); command count 8 → 9, phase count stays 8
  (FR-35).
- `docs/artifacts.md`, `README.md`, `docs/ADOPTING.md`, `sdd-flow/SKILL.md` →
  document the layer, the profile, `deliverables/`, and the new command.
- `tests/validate.sh` → new checks (FR-37–39).
- Three manifests + `CHANGELOG.md` → `0.5.0` (FR-39).

Not touched: `NOTICE`, `spec-generator/SKILL.md`, `spec-template.md`,
`templates/AGENTS.md`, `templates/constitution.md`.

## Data model

No storage. The contract is a set of text formats the modules read and write:

**Docs profile line** (in the project's `AGENTS.md`, SDD section): a line
`Docs profile: lite` or `Docs profile: formal`, optionally as a list item.
Lines inside HTML comments or code fences are "commented" and ignored. Exactly
one active line with a trimmed, case-sensitive value of `lite` or `formal` is
valid; none → `lite` silently; several or another value → warn and `lite`
(FR-2, 3). The template ships the line active once; its explanation sits in an
HTML comment so the literal never appears twice.

**CHG entry** (in `spec.md`, under `## Changes`):

```
### CHG-n — YYYY-MM-DD — <title in plain, business language>

- Type: add | modify | remove
- FRs: FR-a, FR-b
- Reason: <why>
```

`n` = highest `CHG-n` found in the spec + 1, starting at 1. Duplicates are
reported. The date is the approval date. `Later changes` sections are ignored
by every reader.

**validation.md additions**: a line `**Date:** YYYY-MM-DD` under the title,
and an `## Updated files` section (roadmap, schema, or "none"; skipped ones
with the reason). Verdict parsing reads the first line under `## Verdict`: it
is "fulfilled" when it starts with `Spec fulfilled` (case-insensitive); `Spec
NOT fulfilled` or any other text is not.

**Closed feature** (shared test, in the skill): `validation.md` exists, the
verdict is fulfilled, and not stale — stale when the spec's latest `CHG-n`
date is later than `**Date:**`, or the spec has a `CHG-n` and the validation
has no date (FR-41). Output states one of: closed, in progress (no/NOT
fulfilled validation), re-validation required.

**Feature order**: folders linked in `docs/roadmap.md` in the order they first
appear; unlisted folders after them by `NNN`. Several roadmap entries may
share one folder; the first occurrence sets the position (FR-23).

**Generated-document header** (same in every generated file, in the
document's language, FR-25/30):

```
> Derived view generated by /sdd:docs. Do not edit by hand.
> Generated: YYYY-MM-DD
> Sources: <paths>
> If this document disagrees with the specs, plans, or constitution, those prevail.
```

`Generated:` is on its own line so the diff can ignore it (FR-22, 50).

**schema.md**: one block per persistent structure (name, fields with type and
constraints, keys, relationships, notes) in storage-neutral wording, ending
with `## Notes (hand-written)`; everything from that heading to the end of
file is preserved verbatim on refresh (FR-42).

## Algorithms / non-trivial logic

**Document request (skill entry).**

1. Resolve the name: from the command argument, or from natural language. Not
   exactly one of `prd|trd|acceptance|changes|schema` → ask which, write
   nothing (FR-48). `flow`/`ux` → say they are hand-written from the template,
   point to it (FR-34). Missing/unknown name from the command → list valid
   names (FR-17).
2. Schema skips to its own procedure (no profile gate, no closed-feature
   requirement — FR-19, 46). Otherwise resolve the profile; if `lite`, warn
   and ask for confirmation every time; decline → stop (FR-19, 20).
3. Select features per document (below); missing source artifact → name it,
   stop (FR-21).
4. Build the proposal and the review list (FR-27, 28), show it, wait for
   approval (FR-18).
5. Existing target: diff ignoring the `Generated:` line; only that line differs
   → "up to date", write nothing; else show diff, ask (FR-22, 50).
6. `deliverables/` target: if `.gitignore` is missing or doesn't cover it,
   propose adding the entry (creating the file) and wait; declined → still
   write, remind once (FR-31).
7. Write.

**Per document**

- `prd` ← each closed feature's `spec.md`: goal, users, stories, FRs, out of
  scope. Each FR becomes one plain sentence "who benefits / what they get",
  without EARS keywords, `FR-` ids, or file/table/command names (FR-29). NFRs
  and edge cases are not carried over.
- `trd` ← each closed feature's `plan.md`: modules, data model, algorithms,
  decisions, interface contract. Omits Risks and Verification strategy
  (FR-27).
- `acceptance [feature]` ← one closed feature: goal, each requirement as a
  plain sentence with its validated outcome and the validation date, completion
  criteria, and blank sign-off lines. Argument absent → most recently closed
  (latest `**Date:**`); not closed → state why and stop (FR-43, 44). Evidence
  columns and validation notes are not carried over.
- `changes` ← `## Changes` entries of closed features: date, title, type, and
  the FR references. Reason is omitted (FR-27); features with no `## Changes`
  say so instead of reading legacy sections (FR-13).
- `prd`, `trd`, `changes` list non-closed features in one line each: "in
  progress" or "re-validation required" (FR-24); no closed feature → say so,
  stop (FR-45).
- `schema` ← see the schema procedure below.

**Review list (FR-28).** After drafting, the skill re-reads its own draft and
the omitted text, and lists with location: queries, numeric thresholds,
internal identifiers, hostnames, credentials; plus each omitted Reason. This
is a model read, not a parser, so the list is stated as "to review", not as a
guarantee.

**Schema procedure** (used by `/sdd:validate` automatically and by `/sdd:docs
schema` interactively):

1. Find sources: applied migrations first; if none, declared models or schema
   definitions; none at all → skip, report "schema: skipped, no schema source
   found" (FR-6).
2. If migrations and models disagree, note it and follow the migrations
   (FR-49).
3. Build the structure blocks; keep the existing hand-written notes section
   (FR-42); create the file from the template if absent.
4. Interactive mode: diff + approval (FR-22, 50). Automatic mode: write
   without asking only if the content (ignoring `Generated:`) changed, and
   list it in `validation.md` (FR-4, 10, 17).

**Roadmap update** (`/sdd:validate`, fulfilled only):

1. File missing → skip, note in `validation.md` (FR-9).
2. Folder already under Done → unchanged (FR-47). Under Next → move the line
   to Done. Absent → append a Done entry (feature name, one line, folder
   link), numbered after the last Done item (FR-7).
3. No `## Done` heading → skip and note it (not specified by the spec; chosen
   over inventing a heading in someone's file).
4. Not fulfilled → untouched (FR-8, 5).

**`/sdd:change`**: after the diff is approved, append the CHG entry (creating
`## Changes` at the end of the spec if missing). The title must be plain
business language. Not approved → nothing recorded (FR-11, 12).

## Technical decisions

- Skill named `sdd-documents`, not `sdd-docs` → the flat install turns
  `commands/docs.md` into `sdd-docs.md`, so a skill folder `sdd-docs` would
  share a name with it and may collide. Discarded alternative: `sdd-docs`
  (used in earlier drafts) — risk with no benefit; `doc-generator` — loses
  the `sdd-` prefix that avoids clashes with the user's own skills.
- All document logic in the skill; `docs.md` only forwards → Copilot has
  skills but no commands (FR-15). Discarded alternative: logic in the
  command with the skill calling it — Copilot could not run it.
- `validate` calls the skill's schema procedure instead of duplicating it →
  one definition of source priority, notes preservation, and discrepancy
  handling. Discarded alternative: inline steps in `validate.md` — two copies
  drift. Consequence: `validate` depends on the skill; both always install
  together.
- CHG entry format defined in `change.md` (writer) and parsed by the skill
  (reader), not in `spec-template.md` → that file is Apache-2.0 and off
  limits. Discarded alternative: extending the template.
- Verdict and staleness read from plain text lines (`**Date:**`, first line of
  `## Verdict`) → no parser, no dependency (principle 4). Discarded
  alternative: YAML frontmatter in `validation.md` — changes an existing
  artifact format for every project.
- Review list produced by the model → a regex scanner would need a script
  and still miss the cases that matter. Discarded alternative: bash scanner —
  new dependency surface, false sense of safety.
- Test coverage = structural checks in bash + a manual scenario checklist run
  on temporary sample projects → the behaviors are prompts, which a bash test
  cannot execute. Discarded alternative: none available without an LLM in the
  gate.
- Constitution edit limited to the roadmap sentence (FR-51); `docs/
constitution.md` is this repo's own file, not the Apache template.

## Interface contract

`/sdd:docs <prd|trd|acceptance|changes|schema> [feature]` — `feature` (spec
number or folder slug) is read only by `acceptance`.

| Situation                        | Output                                           | Writes                      |
| -------------------------------- | ------------------------------------------------ | --------------------------- |
| Missing/unknown name             | Valid names listed                               | nothing                     |
| `flow`, `ux`                     | "Hand-written from the template" + template path | nothing                     |
| Ambiguous natural language       | Which of the five?                               | nothing                     |
| `lite`, client-facing            | Warning + confirmation each time                 | only after yes and approval |
| Required source missing          | Name of the missing artifact                     | nothing                     |
| No closed feature                | Says so                                          | nothing                     |
| Acceptance of non-closed feature | Verdict or "re-validation required"              | nothing                     |
| Target unchanged except date     | "Up to date"                                     | nothing                     |
| Target exists, content differs   | Diff + question                                  | only after approval         |
| `deliverables/` not ignored      | Proposal to add the entry                        | `.gitignore` after approval |

`/sdd:validate` adds, on a "fulfilled" verdict: roadmap line moved/added,
schema refreshed; both listed under `## Updated files`, plus
`**Date:** YYYY-MM-DD`. `/sdd:change` adds the `CHG-n` entry described above.

## Verification strategy

Automated (`tests/validate.sh`, extended):

- `sdd-documents/SKILL.md` has name = folder and a description; the seven
  templates exist; `commands/docs.md` has a description (FR-33, 36, 38).
- Install smoke (temporary HOME): `skills/sdd-documents/templates/prd.md` and
  `commands/sdd-docs.md` exist after install, idempotency and `--force`
  still pass (FR-37).
- `validate.md` lists `Edit` in `allowed-tools`; `change.md` mentions
  `## Changes`; `AGENTS-sdd-section.md` contains exactly one active `Docs
profile:` line (FR-1, 3, 7, 11).
- Version consistency: all four version strings equal and `CHANGELOG.md` has a
  matching heading (FR-39).
- `claude plugin validate ./plugins/sdd --strict` and the whole script green.
- `git diff --name-only` shows none of the Apache-2.0 files or `NOTICE`.

Manual (temporary sample projects, results recorded in `validation.md`,
nothing committed). Scenarios: profile absent / `formal` / invalid / duplicated;
validate on a project with migrations (schema written, notes kept), with
models only, with none (skipped), with a not-fulfilled verdict (nothing
touched), roadmap missing / already Done / absent entry; change approved and
declined; a `CHG-n` entry newer than the validation (feature excluded);
`prd`, `trd`, `acceptance`, `changes` in `lite` (confirm) and `formal`; repeat
generation (up to date); edit an existing file (diff shown); `deliverables/`
with and without `.gitignore`; natural-language request without a name.
Generation of PRD, TRD, and an acceptance record from this repo's own
artifacts (needs the 001 validation to count as closed — it has no date and no
`CHG-n`, so it does).
Not exercised and reported as such: real opencode and Copilot CLI sessions.

## Risks

- The agent skips or misreads a rule (prompts are not code) → rules phrased as
  numbered steps with explicit stop conditions, and each covered by a manual
  scenario above. Residual risk accepted.
- Review list misses a sensitive item → documents are gitignored and
  approval-gated; the list is labelled as a review aid. Accepted.
- Same-day change after validation is undetected → accepted limit, in the
  spec's edge cases.
- Skill/command name collision in flat installs → avoided by the `sdd-documents`
  name; not tested against a real Claude Code install, so reported as
  unverified.
- Trailing whitespace in the profile value is invisible to a model reading
  the file → the plan trims whitespace and keeps case-sensitivity; the spec's
  edge case was changed to "case variant" to match.
- Removed requirements have no text left in the spec, so the change log
  shows FR references, not sentences → the CHG title is required to be plain
  business language. The client sees `FR-n` there but not in the PRD. Accepted.
- `validate` now writes outside its own artifact without asking → listed in
  `validation.md` and visible in `git diff`; contained by FR-10.
- Roadmap with no `## Done` heading is skipped, not repaired → noted in
  `validation.md`. Accepted.
