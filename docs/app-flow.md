## Actors

- Developer — works with AI agents (Claude Code or opencode) and wants a consistent SDD flow across projects without copying prompts by hand; runs the flow on own, course, or client projects.
- Client / stakeholder — receives the formal documents and never reads specs or plans.
- Toolkit maintainer — edits the toolkit's content in a single place and ships it across Claude Code, opencode, and GitHub Copilot CLI.

## Main journey: Run one command per phase (001 U2)

The developer walks the SDD phases without memorizing prompts.

```text
start → constitution → spec → clarify → plan → tasks → implement Tn (repeat) → validate → [change → back to spec]
```

| Step | Actor     | Action                                      | Result                                                                                                                      |
| ---- | --------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 1    | Developer | Runs `/sdd:constitution`                    | A constitution of short, verifiable principles is proposed; `docs/constitution.md` is written only after approval            |
| 2    | Developer | Runs `/sdd:spec`                            | See the next journey                                                                                                        |
| 3    | Developer | Runs `/sdd:clarify`                         | Ambiguities, contradictions, missing edge cases, and conflicts with the constitution are listed, without solutions          |
| 4    | Developer | Runs `/sdd:plan`                            | `specs/NNN-<slug>/plan.md` is generated (modules, data model, justified decisions, risks, verification strategy), no code   |
| 5    | Developer | Runs `/sdd:tasks`                           | `specs/NNN-<slug>/tasks.md` is generated, ordered by dependency, each task with its FRs, a checkbox, and a "Done when:" line |
| 6    | Developer | Runs `/sdd:implement <n>`                   | Only task Tn is implemented, verification first, run, marked, and the command stops                                          |
| 7    | Developer | Runs `/sdd:validate`                        | The spec is walked FR by FR, `specs/NNN-<slug>/validation.md` is written, and a compliance verdict is issued                 |
| 8    | Developer | Runs `/sdd:change <requirement>`            | The spec is updated first and the diff is shown, without touching code                                                      |

## Main journey: General journey

Requirements that match no user story.

```text
start → request a document from /sdd:docs (one of eight names) → flow or ux: generated, not written by hand → end
```

| Step | Actor     | Action                                               | Result                                                                                                                                  |
| ---- | --------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Developer | Requests `flow`, `ux`, or `delivery` from `/sdd:docs` | They are accepted as valid names alongside the five existing ones (003 FR-1)                                                            |
| 2    | Developer | Requests `flow` or `ux`                              | The document is generated instead of the user being told to write it by hand (003 FR-2; replaces 002 FR-34)                             |

Applies to every journey:

- The SDD artifacts from the toolkit's own build (`docs/constitution.md`, `specs/001-sdd-toolkit/`) are in the repo as a living example (001 FR-20).
- The PRD, TRD, and scope change log include only closed features, ordered as in `docs/roadmap.md` or else by spec number; each excluded feature is listed in one line as in progress or re-validation required (002 FR-23, FR-24).
- `deliverables/` is documented as excluded from deploy, alongside `docs/` and `specs/`, in the adoption guide and the SDD section template (002 FR-32).
- The schema document is internal: the client-facing rules do not apply to it (002 FR-46).
- Templates for `docs/app-flow.md`, `docs/ux-brief.md`, and `docs/schema.md` ship inside the document-generation skill's own folder, so the skill works installed alone on Claude Code, opencode, and Copilot CLI (002 FR-33, FR-36).
- The SDD flow stays at eight phases; document generation is a cross-cutting action, not a phase (002 FR-35).
- `install.sh` run against a temporary home installs the new command with the `sdd-` prefix and the skill under its own folder; `tests/validate.sh` covers the command, skill, and templates (002 FR-37, FR-38).
- Version `0.6.0` is published in `plugin.json` and the manifests, with its `CHANGELOG.md` section (003 FR-30; 0.5.0 was 002 FR-39).
- The roadmap sentence of constitution principle 3 says the roadmap is maintained by hand or by `/sdd:validate`, with no other statement left saying it is purely by hand (002 FR-51).
- The `lite` gate does not apply to `ux`, and `ux` does not require a closed feature (003 FR-12).
- `flow` and `ux` are written through the schema document's write path: header, diff against an existing file, explicit approval, no `.gitignore` check (003 FR-21).
- The `flow` and `ux` templates carry a `## Notes (hand-written)` section and the derived-view header instead of the "written by hand" banner (003 FR-25).
- The `/sdd:docs` command, the `sdd-documents` and `sdd-flow` skills, `docs/artifacts.md`, `README.md`, the roadmap, and `CHANGELOG.md` no longer describe `flow`, `ux`, and `delivery` as hand-written or missing, and the `lite` gate and client-facing rules cover `delivery` (003 FR-29).
- The templates, including `templates/delivery.md`, ship inside the `sdd-documents` skill so the feature works on Copilot CLI, opencode, and flat installs (003 FR-31).
- Content other than a `TODO: provide …` gap in an existing `flow` or `ux` section is kept when the artifacts give no source for it (003 FR-32).
- The validation template has an optional `## Known limits` section, which `/sdd:validate` writes only with product restrictions a client may read, never verification gaps (003 FR-33).

## Alternative paths

- Install script receives an unrecognized `--target`, no `--target`, or `--target` with no value — it prints usage and exits with status 1 (001 FR-8).
- A destination file already exists and differs from the source — the install script skips it and reports it, unless `--force` is passed (001 FR-6).
- `/sdd:plan` runs without `docs/constitution.md` or without an active spec — it warns and stops (001 FR-13).
- `/sdd:implement` runs without a number — the command asks for it and does not assume T1 (001 clarification 6).
- Verdict is not "fulfilled" — `docs/schema.md` and `docs/roadmap.md` stay unchanged (002 FR-5, FR-8).
- No definition of persistent data structures is found — the schema update is skipped, `schema: skipped, no schema source found` is recorded in `validation.md`, and the verdict is unchanged (002 FR-6).
- Migrations and declared models disagree — the discrepancy is noted in `validation.md` and the applied migrations are followed (002 FR-49).
- `docs/roadmap.md` does not exist — the roadmap update is skipped and noted in `validation.md` (002 FR-9).
- Feature is already listed as Done — the roadmap stays unchanged (002 FR-47).
- `/sdd:docs` receives a missing or unknown name — it lists all eight valid names and generates nothing (002 FR-17, 003 FR-3).
- A natural-language request does not identify exactly one document — it asks which one and generates nothing yet (002 FR-48, 003 FR-4).
- The user declines the `lite` confirmation — nothing is written (002 FR-20).
- A source artifact required by the document is missing — it names the artifact and generates nothing (002 FR-21).
- The target file exists — the changes are shown against it, ignoring the generation-date line, and it is overwritten only after approval; if only the date would change, the file is reported as up to date and nothing is written (002 FR-22, FR-50).
- No closed feature exists — it says so and generates nothing (002 FR-45).
- The feature requested for the acceptance record is not closed — it states why and generates nothing (002 FR-44).
- A spec's latest `CHG-n` date is later than its validation date, or it has a `CHG-n` and the validation records no date — the feature is treated as not closed (002 FR-41).
- The user declines adding `deliverables/` to `.gitignore` — the document is still written and the user is reminded once (002 FR-31).
- A `flow` template section has no source, such as screens or views — a `TODO: provide …` gap is written instead of invented content (003 FR-7).
- `flow` is requested with no closed feature — it says so and generates nothing (003 FR-9).
- `delivery` is requested with no closed feature — it says so and generates nothing (003 FR-19).
- An existing `flow` or `ux` file has no notes heading — an empty notes section is written and the user is told the previous content was replaced (003 FR-24).
- A template the requested document needs is missing — it names the template and generates nothing (003 FR-34).

## Error and empty states

- Install script with neither `~/.config/opencode/` nor `~/.claude/` — it creates the paths (001 edge case).
- Installed file modified by the user — skipped and reported without `--force` (001 FR-6).
- Corrupt `marketplace.json` or `plugin.json` — the quality check exits with status 1 and lists each failure (001 FR-19).
- Invalid or duplicated `Docs profile` value, such as `Formal` or two active lines — reported in the command output; `lite` applies (002 FR-3).
- Project without persistent data — no schema update, the flow continues (002 FR-6).
- Closed feature with no `## Changes` section — the scope change log says it has nothing to derive from it (002 edge case).
- Feature with a missing, "NOT fulfilled", or outdated validation — excluded from client documents and listed in one line (002 FR-23, FR-24, FR-41).
- Schema document edited by hand and then refreshed — structures follow the migrations or definitions; the notes section is preserved (002 FR-42).
- Document generated twice in a row with no other changes — reported as up to date, nothing written (002 FR-50).
- Parallel branches that both add `CHG-n` entries — duplicates are reported, not merged (002 FR-12).
- Change made after validation on the same day — not detected as stale; known limit, accepted (002 edge case).
- `flow` with no closed feature, or `delivery` with no closed feature — told there is none; nothing is generated (003 FR-9, FR-19).
- Unknown or missing document name — the eight valid names are listed (003 FR-3).
- Missing template — the template is named and nothing is generated (003 FR-34).
- Closed feature with no user stories — its journey section is a gap (003 edge case).
- Project with no `docs/constitution.md` — `ux` writes language and accessibility as gaps and the content language follows the user's (003 edge case).
- Feature that needs re-validation when `delivery` is requested — listed as not closed (003 edge case).
- `flow` or `ux` existing as a hand-written file from 0.5.0 — content without a source is kept; with no notes heading, an empty notes section is written and the replacement is reported (003 edge case, FR-24, FR-32).
